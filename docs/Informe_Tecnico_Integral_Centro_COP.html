1. Resumen ejecutivo

Dictamen. Centro COP es una plataforma clínica modular, con una API NestJS como núcleo transaccional, MongoDB y Redis, sitios Next.js para la experiencia actual y frontends Angular conservados como legado. La plataforma ya incorpora un microservicio Spring Boot para J48; mantener una arquitectura políglota es técnicamente justificado para los componentes de IA. No se recomienda migrar todo el backend a Spring Boot ahora: no hay un bloqueo técnico que lo exija y el cambio introducirá alto riesgo clínico y operativo. La prioridad es consolidar las rutas activas, retirar o aislar los stubs y cerrar brechas de producción.

Conclusiones prioritarias

  1. La API NestJS cubre IAM, pacientes, historia clínica, citas, odontología, psicología, pagos, tenancy, analítica, IA y compatibilidad.
  2. El gateway enruta API, sitio público, J48 y servicios IA; los servicios IA del perfil ai no forman parte del arranque core.
  3. Existen funciones explícitamente stub o de compatibilidad (diagnóstico/emoción y Fotos→3D en desarrollo); no deben anunciarse como capacidad clínica productiva hasta su integración y validación.
  4. La configuración de producción valida secretos, CORS y webhooks, pero el compose mantiene credenciales de desarrollo que deben quedar fuera de cualquier despliegue real.

Datos y límites de confianza

MongoDB conserva entidades clínicas y administrativas; Redis soporta revocación de JWT y procesamiento. El TenancyInterceptor y los módulos de IAM indican segregación por organización. Debe comprobarse con pruebas de autorización por recurso, porque una estructura de módulos no demuestra por sí sola el aislamiento efectivo en todas las consultas.

J48: coexistencia Python y Spring Boot

La implementación Python es la ruta operativa actual. La Java implementa una alternativa Weka más estructurada: /health, /info, /predict, /predict/explanation y /train. Antes de reemplazar Python por Java hay que igualar explícitamente los contratos de árbol, métricas, entrenamiento, autenticación entre servicios y rendimiento. La coexistencia actual es válida, pero debe decidirse un único servicio propietario antes de escalar.

4. Seguridad, privacidad y operación

Controles presentes

  • Helmet, CORS, validación con whitelist y rechazo de campos no permitidos.
  • Guard global de throttling, JWT y RBAC.
  • Swagger solo fuera de producción.
  • Health profundo para Mongo/Redis y liveness separado.
  • Validación de producción para JWT, CORS, Mongo y webhook Wompi.

Riesgos observados

  • Valores de desarrollo en compose.yaml, incluidos password Mongo y JWT_SECRET=change_me.
  • Mongo y Redis se publican en puertos locales: no exponerlos en un host compartido.
  • CORS permite previews Vercel por defecto; conviene deshabilitarlo si no es necesario.
  • Autenticación servicio-a-servicio no queda demostrada para todos los microservicios IA.

Privacidad y uso clínico

El servicio J48 Java declara minimización de datos para la explicación generativa: solo envía variables desidentificadas y puede usar fallback local si el proveedor está deshabilitado. Para toda la plataforma se recomienda formalizar un inventario de datos, finalidad, retención, responsables, consentimiento, trazabilidad de accesos y procedimiento de incidentes conforme a la normativa aplicable de datos de salud en Colombia. Esta revisión no constituye certificación legal ni auditoría de cumplimiento.

Observabilidad y continuidad

Hay health checks y logs de arranque, pero no se observó integración de APM/Sentry ni una estrategia comprobada de logs estructurados, backups/restore de Mongo, RPO/RTO o alertas de producción. Son requisitos de salida antes de operar datos clínicos reales.

Casos mínimos que faltan por automatizar

  • Reserva pública completa y webhook Wompi firmado en sandbox.
  • Aislamiento de datos de una organización frente a otra en todos los endpoints de pacientes, citas e historia.
  • Autorización por rol y por sede para acciones sensibles.
  • Fallos de Redis/Mongo, recuperación y revocación de token.
  • Contrato de Nest con J48 Python/Java y regresión del modelo sobre dataset versionado.
  • Flujo de imagen/DICOM contra un proveedor real, nunca contra el stub.

6. Decisión: ¿migrar todo a Spring Boot?

Decisión recomendada: no realizar una migración big-bang. La API NestJS ya concentra el dominio y los frontends consumen sus contratos. Migrarla completa a Java duplicaría 216 puntos HTTP potenciales, entidades Mongo, reglas RBAC, pagos, WebSocket, colas e integraciones. En una plataforma clínica, el riesgo de regresión supera el beneficio si no existe un requisito explícito de organización, soporte o rendimiento que NestJS no pueda cumplir.

Ruta segura si se decide migrar J48

  1. Definir contrato OpenAPI único y tests de consumidor para /predict, árbol, métricas y entrenamiento.
  2. Ejecutar ambos servicios en paralelo, con entradas desidentificadas y comparación de resultados.
  3. Versionar dataset, modelo, métricas, umbrales, fecha de entrenamiento y aprobación clínica.
  4. Canary interno con rollback mediante J48_URL; no cambiar el comportamiento de pacientes sin aprobación.
  5. Retirar Python solo cuando la paridad, seguridad y monitoreo estén demostrados.
